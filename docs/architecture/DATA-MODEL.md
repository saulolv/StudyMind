# Data and storage model

Five stores, each with exactly one owner. This document says what is in each of them, and why the
things that are *not* in them are elsewhere.

## content_db — owned by content-service

One table. It is the inventory: what material a user has and what state it is in.

```sql
create table content (
    content_id       uuid         primary key,
    user_id          uuid         not null,
    type             varchar(16)  not null,   -- PDF | VIDEO
    status           varchar(16)  not null,   -- PENDING | PROCESSING | INDEXED | FAILED
    file_name        varchar(512),
    storage_path     varchar(1024),
    source_url       varchar(2048),
    title            varchar(512),
    duration_seconds integer,
    created_at       timestamptz  not null,
    updated_at       timestamptz  not null
);
```

The migration lives in
[`V1__create_content.sql`](../../services/content-service/src/main/resources/db/migration/V1__create_content.sql).
Three constraints carry the design:

- `content_type_check` and `content_status_check` pin the two enumerations in the database, not only
  in Java. A worker writing a status by hand cannot invent a fifth state.
- `content_source_check` makes the discriminator carry its own integrity: a `PDF` row must have
  `storage_path` and `file_name`, a `VIDEO` row must have `source_url`. The nullable columns are not
  optional — they are conditional on `type`, and the database knows the condition.
- `idx_content_user_created` on `(user_id, created_at desc)` is the listing query. There is no index
  that does not start with `user_id`, because there is no query that is not scoped to a user.

### One status, not two

The old video-service carried `transcript_status` alongside `status`. Under a unified content model
transcription is simply the `PROCESSING` stage of a `VIDEO`, so the second column is gone. Both
types walk the same four states:

```
PENDING ──▶ PROCESSING ──▶ INDEXED
   │             │
   └─────────────┴────────▶ FAILED
```

`PENDING` is set by ingestion. The transitions after it belong to the workers — which is the gap
noted in [ARCHITECTURE.md](ARCHITECTURE.md#where-this-design-is-currently-weak): no failure event
contract exists yet, so nothing currently drives a row to `FAILED`.

### Why `content_id` is generated by the application

Ingestion mints the UUID before it writes anything, because the storage key
(`raw/{user_id}/{content_id}/{file_name}`) needs it before the row exists, and the event needs it to
match the row. A database-generated id would force a write, a read-back and a second write.

## auth_db — owned by api-gateway-auth

Not yet implemented. The shape the checked-in
[OpenAPI spec](../../services/api-gateway-auth/openapi/openapi.yaml) implies:

| Table | Holds |
| --- | --- |
| `app_user` | `user_id`, `email` (unique), `password_hash`, `full_name`, `role`, timestamps |
| `refresh_token` | the hash of an issued refresh token, its user, its expiry, and whether it was revoked |

Refresh tokens are stored hashed and revoked by row, not by keeping a denylist in a cache — see
[ADR-0003](adr/0003-remove-redis-until-something-needs-it.md) for why that decision is recorded
rather than assumed.

## chat_db — owned by chat-llm-service

Not yet implemented. The shape its
[OpenAPI spec](../../services/chat-llm-service/openapi/openapi.yaml) implies:

| Table | Holds |
| --- | --- |
| `chat_session` | `session_id`, `user_id`, `title`, timestamps |
| `chat_message` | `message_id`, `session_id`, role, content, and the `chunk_ids` the answer cited |

Citations are stored as the chunk ids, not as copied chunk text. The text belongs to Qdrant; copying
it here would create a second source of truth that goes stale when material is re-indexed.

## Object storage — owned by content-service

MinIO in development, S3 in production: the same adapter with a different endpoint, which is why
there is no `FileStorage` port in the code — see the note on `BlobStore` in
[the content-service guide](../development/02-content-service.md).

```
{bucket}/raw/{user_id}/{content_id}/{file_name}
```

Three properties matter about that key:

- **`user_id` first.** A key cannot be constructed that lands in another user's prefix, which makes
  a per-prefix policy possible later without a migration.
- **`content_id` second.** Two uploads of `lecture.pdf` by the same user do not collide.
- **The file name is sanitised, not trusted.** Path separators are stripped, anything outside
  `[A-Za-z0-9._-]` is replaced, names that sanitise to nothing usable are rejected, and the result
  is truncated to 200 characters so the key fits `storage_path`. `../../../etc/passwd.pdf` becomes
  `passwd.pdf` inside the user's own prefix.

Only the *raw* upload is stored. Extracted text and chunks are not, which is the subject of
[ADR-0002](adr/0002-chunks-are-a-storage-artifact.md).

## Qdrant — written by embedding-worker, read by chat-llm-service

One collection, named in the `ContentIndexed` event so the reader does not have to hardcode it.
Each point is one chunk:

| Field | Purpose |
| --- | --- |
| `id` | the chunk id, a UUID, also carried in `ChunksCreated` |
| `vector` | the embedding |
| `payload.user_id` | **the tenant filter**, applied before similarity is considered |
| `payload.content_id` | which material the chunk came from, for citations and for deletion |
| `payload.type` | `PDF` or `VIDEO` |
| `payload.text` | the chunk text, so retrieval does not need a second round trip |
| `payload.page` | PDF only |
| `payload.start_seconds`, `payload.end_seconds` | video only, and what makes a timestamped answer possible |

`user_id` in the payload is load-bearing. A vector search without that filter would return the
nearest chunks in the whole system, and the fact that they are nearest makes them worse, not
better: they would be the most convincing possible leak.

## Deletion

`DELETE /contents/{contentId}` removes the row and publishes `ContentDeleted` with a 202. That
status is honest: the row is gone synchronously, and the rest is not.

| What | Removed by | When |
| --- | --- | --- |
| the `content` row | content-service | synchronously, in the request |
| the raw PDF blob | a consumer of `ContentDeleted` | asynchronously |
| the Qdrant points for that `content_id` | a consumer of `ContentDeleted` | asynchronously |

The consumers do not exist yet, so today the event is published and nothing acts on it. That is a
known gap, not a design in which blobs are meant to persist.
